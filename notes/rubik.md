## Origin and interface

The starting point is the student's Homework 1 solver at
[Edison1019/minirubik](https://github.com/Edison1019/minirubik/blob/4b2952495e2e21109533c27dc4200985b94ab5b7/solver.c).
Its corner coordinates, permutation/orientation transition tables, coordinate
lower bounds and input model are retained. The upstream license is preserved
as `src/rubik/LICENSE.minirubik`. The search frontier, Bloom filter, suffix
reconstruction, buffer interface and hand-written assembly are implemented
for this assignment. The assembly is independent of the C function.

`rubik_solve(state, out, cap)` parses seven permutation digits and seven
orientation digits. The permutation contains each digit 1..7 exactly once.
Orientations are digits 1..3 whose zero-based values sum to a multiple of 3.
The function returns a shortest move count and writes single-space-separated
move names, including a terminating NUL. It returns -1 for invalid input and
leaves out untouched. An insufficient buffer returns -2 and writes an empty
string only when cap is nonzero. The required length is checked before any
successful-path output is copied. The solved cube returns zero and requires
one byte for the empty string.

## Coordinates and lower bounds

Fixing one corner removes whole-cube rotation. The remaining permutation has
7! = 5,040 possibilities. Six independent twists have 3^6 = 729 possibilities;
the seventh is fixed by the twist-sum constraint. Thus there are exactly
5,040 * 729 = 3,674,160 states.

A permutation is ranked by Lehmer digits: at each position count smaller
unused values and accumulate in the descending mixed radix. The first six
orientations are a base-three integer. The C port produces these coordinates
separately, avoiding the previous division and remainder by 729. The assembly
counts unused values below the digit with a seven-bit mask and implements
the small radix products with addition, without a multiply or divider.

Quarter-turn tables are `perm_trans[5040][3]` and `ori_trans[729][3]`, each
using 16-bit entries. Repeating a quarter turn produces the half and inverse
turns. Two byte tables hold exact distances in the projected permutation
and orientation graphs. Every full-cube solution projects to a path in both
graphs, so h(p,o)=max(hp[p],ho[o]) is admissible.

## Search and proof of optimality

The original nonrecursive IDA* searched all the way to solved. The new version
stores every state at distance at most five from solved, then searches only
the prefix. For a bound b>5, it expands at most b-5 edges and checks whether
the remaining state has a table distance at most five. The diameter is 11,
so at most six prefix edges are needed.

Bounds increase from max(6,h) after a root-table miss. A separate sorted table
identifies the 2,644 states at exact distance 11, permitting those states to
start directly at bound 11; all other states need at most bound 10. This
classification is complete, generated by a host BFS over all states.

Adjacent moves on the same face are omitted because they combine into one
move or cancel. No shortest path is lost. If a shortest path has length b,
its state after b-5 moves is within five moves of solved and is in the suffix
table. Admissible pruning cannot remove that prefix. Therefore increasing
bounds returns a shortest solution. The root table directly handles distances
zero through five. Following each stored inverse move decreases table
distance by one, so suffix reconstruction terminates at solved.

The BFS is a host-side generation step only. No full-state distance array,
queue, or full-state solution table is stored or constructed on RV32I.

## Tables and encoding

A state key is `(p << 10) | o`. Ten bits accommodate every orientation; unlike
p*729+o, this key needs no multiplication and stays below 2^23. A near entry is

```
(key << 7) | (distance << 4) | next_move
```

Distance needs three bits and a move index needs four. The solved entry uses
move sentinel 15 and distance zero. Binary search compares entry >> 7 with
the key. This packs membership, exact distance and one move toward solved in
a single word. A separate full solution string for each entry is unnecessary.

| Table | Entries | Bytes |
| --- | ---: | ---: |
| Permutation quarter-turn transitions | 5040 x 3 | 30240 |
| Orientation quarter-turn transitions | 729 x 3 | 4374 |
| Permutation lower bound | 5040 | 5040 |
| Orientation lower bound | 729 | 729 |
| States at distance at most 5 | 12224 | 48896 |
| States at distance exactly 11 | 2644 | 10576 |
| Bloom filter | 2048 words | 8192 |

The Bloom index is `(key ^ (key >> 10) ^ (key >> 16)) & 65535`. All near keys
set their corresponding bit during generation. A zero bit proves absence;
a set bit always leads to exact binary search. False positives cost time but
cannot produce a wrong answer, and there are no false negatives. It avoids
most unsuccessful binary searches at the depth frontier.

`mytests/rubik_generate.c` reproduces the tables and hard-state cases from the
Homework 1 transition tables. It checks full reachability, diameter 11 and
the expected near/diameter counts before emitting the files. Assembly has its
own table definitions in `tables.inc`, included with GNU assembler `.include`;
it never references the C tables. The two implementations are measured
separately, as required by the harness.

## RV32I implementation and stack

Table row addresses use p*6 = (p<<1)+(p<<2). Coordinates remain in registers;
state keys use shifts and OR. Assembly lookup is a leaf routine and shares
read-only table bases in s6..s11 with the private search helpers. The public
entry saves and restores every callee-saved register. Private recursive
frames preserve the mutable s registers they use.

The main assembly frame is 160 bytes. Six expanded levels use 48 bytes each;
a frontier frame and suffix reconstruction each need 32. The implementation
therefore needs at most 512 bytes of stack below its public entry, leaving
room in the 4 KiB stack for the caller and runtime. C disassembly shows
80-byte search frames and public-entry frames of at most 96 bytes across
these builds, also comfortably within 4 KiB with the bounded recursion.
There is no heap, CSR access, environment call, floating-point instruction,
compressed instruction, or hardware multiply/divide in either implementation.
The C compiler may call the permitted software `__mulsi3` for ranking.

## Validation

The host C version passed 23 tests under AddressSanitizer and UBSan. Every
RV32I build passed 52 official tests, including exact shortest lengths at all
12 distances, independent replay of the returned moves, all nine one-move
scrambles, a descending 11-move chain, invalid inputs, buffer exact fits and
one-byte-short cases, and C/assembly cross-checks.

Additional tests outside src cover 5,978 states: all 2,644 at distance 11,
2,592 at distance 10, and 742 at shorter distances. They are chosen from the
host BFS by complete diameter coverage, regular sampling among distance-10
states, and a fixed stride through the full coordinate space. No case is
chosen from benchmark behavior. For every case at all four optimization
levels, both versions meet their instruction budget, return the BFS distance,
and produce moves replayed by the independent model in tests/trubik.c.

The maximum measured instruction counts in that extended set are:

All maxima occurred at `54721631111111`, an 11-move state. C's limit is

## Optimization measurements

Measured 2026-11-13 with xPack GCC 15.2.0, binutils 2.45, and rv32emu revision
`9dbff65c4d6a40d64d3bbb38f4c5a20d6e885e24`. Compilation uses
`-march=rv32i_zicsr -mabi=ilp32 -ffreestanding -fno-pic
-fno-stack-protector` and the optimization level below. System interpreter
mode and ELF loading are enabled, while M/A/F/C extensions are disabled.

On the official six benchmark states, the initial direct C port measured
174146.1667 net cycles per solve at O2. The final C search measured 29587.0000,
a 5.886x improvement. This compares the same C API and inputs; the change is
principally the five-step frontier, diameter classification and Bloom filter,
not an isolated instruction substitution. No separate numerical gain is
claimed for each of those combined changes.

Final net cycles per call are `(cycles - measured loop overhead)/6`:

| Build | C | Assembly |
| --- | ---: | ---: |
| O1 | 32881.8333 | 23895.3333 |
| O2 | 29587.0000 | 23894.1667 |
| O3 | 28618.8333 | 23896.6667 |
| Os | 32009.5000 | 23894.5000 |

The best C build is O3. Assembly is 1.198x faster in the same ELF, about a
16.5% reduction in net instructions. O3 spends more text on the C search,
while the assembly keeps lookup and transitions compact, shares table-base
registers and avoids a redundant final suffix lookup. O2 assembly beats the
O2 C baseline by 1.238x. The caller and overhead code account for the small
variation in measured assembly averages; its object is identical in all ELFs.

Input and timed regions are identical for both versions. Parsing and output
buffer construction are part of the solver API and are timed in both;
harness initialization and printed output are excluded. Counter reads and
loop overhead follow the provided harness convention. Counts are deterministic
and use 64-bit differences. rv32emu counts guest instructions, not physical
pipeline latency, cache misses or stalls; these figures must not be presented
as real processor timing or hardware cache benefits.

## Applications

Pattern databases and bounded meet-in-the-middle search apply to shortest
paths, planning and puzzle solving with small deterministic state spaces.
Admissible abstractions preserve optimality; compact exact tables reduce the
search frontier. Bloom filters are useful when most membership queries miss
and false positives can safely fall back to an exact check. On embedded
processors, table size and stack depth must be budgeted explicitly rather
than relying on a large heap.
